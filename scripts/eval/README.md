# Calibration harness for `src/lib/describe.ts`

Measures whether the macro estimator is **biased**, and whether that bias is
**constant across food types**. It is not a pass/fail test and it is not wired
into `npm test`.

```bash
nvm use 24.11.0          # the .ts import needs type stripping (>=22.6)
npm run eval:describe                 # prints the call count and stops
npm run eval:describe -- --confirm    # spends it: 23 fixtures x 3 repeats
npm run eval:score                    # scores the newest run
```

`EVAL_REPEATS=1` for a cheap smoke run. Raw responses land in `runs/`
(gitignored) so re-scoring is free when the metric set turns out to be wrong.

## What the numbers mean

Published vision-LLM error on food is **35–40% MAPE**, and that is *at parity
with trained dietitians looking at the same photographs* — one study of 38
nutrition professionals found portion-size error of 44–48%, and a crowdsourcing
study found experts were not statistically better than average laypeople. So:

- **30–40%** on kcal is state of the art, not a failure.
- **Below 25%** would be genuinely good for text descriptions.
- **Below ~20%** is more likely a ground-truth artifact than a real win.

The headline pair is **median signed % error** (bias) and **IQR** (spread),
always read together. `describe.ts`'s own cache comment argues from S35 that a
biased-but-stable estimator beats an unbiased-but-noisy one, because systematic
logging error is absorbed into the inferred TDEE and cancels out of the deficit.
That is correct — and it means bias and spread have *different costs* and must
never be fused into one MAPE number.

The **stratum table is the real deliverable.** S35's cancellation only holds if
the bias is the same for every food type. Bias that varies by food type is not
bias, it is noise correlated with diet composition — and diets shift exactly
when someone starts dieting.

**Protein is held tighter than kcal.** Nothing cancels a protein error; there is
no adaptive loop behind the protein target.

## Fixtures

`fixtures.json` is generated by `build-fixtures.mjs` from the local Canadian
Nutrient File extract (Health Canada lab values, Open Government Licence). That
extract lives under `tools/`, which is in `.git/info/exclude` — so the generator
only runs on a machine that has built the Philippine catalog, and its output is
checked in with real numbers so nothing at eval time needs it.

Two strata are **empty and hand-entered**:

- `chain` — read each number off the chain's own Canadian nutrition page, and
  record the URL and the date. Not from an aggregator: three of them returned
  520, 550 and 560 kcal for the same Canadian Big Mac in one search, which is a
  wider spread than the model error being measured.
- `packaged` — read off a panel on a box you own. Note that CFIA permits ±20%
  on declared values, so a packaged fixture carries ±20% of reference error
  before the model says anything.

`rules` are scored right/wrong and never pooled into the error metrics. They
guard the `too_vague` path and the multi-portion rule that `describe.ts` calls
the most important line in its prompt — a regression there is invisible in an
average, because every number stays plausible.

## What this cannot tell you

- **Whether the reference is right.** You cannot measure a model error smaller
  than your reference error. CNF singles are ±5%; a package panel is ±20%.
- **Anything about restaurant plates or mixed dishes** — which is where the real
  error lives. There is no free weighed ground truth for a plate of poutine.
  Only weighing your own dinner fixes this.
- **Anything about the photo path.** The runner sends text only. A photo suite
  needs photos of food *you weighed*; a stock image of a chain item has no
  verified relationship to the published panel.
- **Whether the description matched the plate.** In real use that is probably
  the larger error term, and no fixture work touches it.
- **Whether `too_vague` is calibrated.** The three `vague-*` rules test that it
  fires, not the false-abstention rate.
